## Как работают веб-сессии

Регистрация и вход выполняются по email. Адрес приводится к нижнему регистру
без пробелов по краям; повторная регистрация такого же email запрещена.
Пароли хранятся в виде хешей Argon2id.

После успешного входа сервер создаёт сессию и передаёт браузеру случайный токен
в HttpOnly-cookie. В PostgreSQL сохраняется только HMAC-SHA256 хеш токена,
идентификатор пользователя и срок действия сессии. Сам токен в базе не хранится.

Браузер отправляет cookie с последующими запросами. Сервер вычисляет хеш токена,
находит сессию и проверяет её срок действия, активность пользователя и необходимые
permissions через роли пользователя. Если до истечения осталось не больше половины
срока, сессия
продлевается, а cookie обновляется.

У пользователя может быть несколько независимых сессий — например, на телефоне
и компьютере. При выходе удаляется только текущая сессия; остальные устройства
сохраняют доступ. Истёкшая или удалённая сессия больше не позволяет авторизоваться.

Срок действия задаётся в `SESSION_EXPIRATION_MINUTES`, а секрет для хеширования —
в `SESSION_TOKEN_HASH_SECRET`. По умолчанию cookie передаётся только по HTTPS;
для локального HTTP используются `SESSION_COOKIE_NAME=session` и
`SESSION_COOKIE_SECURE=false`.

## API

### Формат ответов

Успех: `{"data": ...}`. Ошибка: `{"error": {"code": "...", "message": "..."}}`.
Необязательный `error.details` содержит список проблем с полями:
`{"field": "...", "code": "...", "message": "..."}`. Ответ `204` не содержит тела.
Возможные ошибки каждого endpoint и примеры ответов указаны в Swagger.

### Добавление ошибок

1. Создай наследника `ApplicationError` в `application/errors.py` со стабильным
   английским `code` и русским `message`; вызывай его через `raise` в бизнес-логике.
2. Добавь соответствие класса и HTTP-статуса в
   `presentation/http/base/error_status_codes.py`.
3. В декораторе endpoint перечисли возможные ошибки:
   `responses=get_error_responses(MyError, ...)`.

Для endpoint с проверяемым телом или параметрами запроса передай
`include_input_errors=True` в `get_error_responses`: это добавляет описание
400/422 в Swagger, не влияет на саму проверку данных. По умолчанию флаг выключен.
Описание 500 добавляется всегда.

### General
- '/': Открыт для **всех**
   - Перенаправляет на Swagger документацию

### Auth (`/auth`)

- 'signup' (POST): Открыт для **всех**
  - Регистрация аккаунта
- 'login' (POST): Открыт для **всех**
  - Вход в аккаунт
- 'logout' (DELETE): Открыт для **всех**
  - Выход с аккаунта

### Hello world (`/hello_world`)
- 'user' (GET): Требует `user_hello_world.view`
  - return: Hello world by user
- 'admin' (GET): Требует `admin_hello_world.view`
  - return: Hello world by admin

Seed-миграция `0002_seed_roles` создаёт роли и разрешения.
Тестовых пользователей можно создать отдельно: `just seed-users` локально или
`just seed-users docker` в запущенном Docker-стеке. Существующие записи пропускаются.

| Роль | Email | Пароль |
| --- | --- | --- |
| admin | `admin@example.com` | `admin-test-password` |
| user | `user@example.com` | `user-test-password` |

## Переменные окружения
Для работы проекта необходимо настроить переменные окружения. В корне проекта подготовлены шаблоны:
- `.env.example` — используйте для локального запуска сервисов (localhost).
- `.env.docker.example` — используйте для запуска всего стека через Docker Compose.

Скопируйте нужный шаблон в соответствующий файл (`.env` или `.env.docker`) и заполните актуальные значения перед запуском.

При локальном запуске `just dev` загружает `.env` через uv.
В Docker переменные окружения передаются через Compose.

## Как запустить
1. Склонируй проект и установи uv, just и Docker Compose.
2. Заполни `.env` для локального запуска или `.env.docker` для полного стека.
3. Локально: `just dev` — PostgreSQL, миграции, тестовые пользователи и приложение.
4. В Docker: `just migrate docker`, затем `just up`.
5. Остановка: `just down local` или `just down`. Список команд: `just`.

В Docker миграции запускаются вручную. В локальном `just dev` миграции и создание
тестовых пользователей выполняются автоматически; существующие записи пропускаются.

## CodeGraph для работы с AI-агентами

Проект использует локальный CodeGraph, чтобы Codex, Claude Code, Gemini, Cursor
и другие AI-агенты могли находить связи между файлами, символами и вызовами без
повторного чтения всего репозитория.

После клонирования перейди в корень проекта, установи CLI и один раз создай
индекс:

```bash
npm install -g @colbymchenry/codegraph
codegraph init
codegraph status
```

Команда `codegraph status` должна показать актуальный индекс. Данные хранятся
только локально в `.codegraph/` и не попадают в Git. Индекс автоматически
обновляется при изменении файлов.

Любой агент может использовать универсальную команду:

```bash
codegraph explore "authentication login flow"
```

Нативное MCP-подключение настраивается отдельно в используемом клиенте и не
хранится в репозитории. Правила работы AI-агентов с проектом описаны в
`AGENTS.md`.

## Проверки кода

Зависимости: `uv sync --all-groups` (версия Python задана в `.python-version`).
`just check` проверяет Ruff, форматирование и mypy.
Проверки перед коммитом без автоисправлений: `uv run pre-commit install`.
Проверяются приложение и `tests/`; служебные файлы Alembic исключены.
Pre-commit запускает статические проверки, без выполнения тестов.

## Автотесты

```bash
just test
just test-no-cov
just test-no-cov tests/unit/application/interactors/test_log_in.py
```

`just test` запускает весь набор через pytest-xdist (`-n auto`) на доступных
ядрах, собирает покрытие строк и ветвлений и требует минимум 90% общего покрытия.
В консоли видны непокрытые строки; отчёты сохраняются в `htmlcov/index.html`
и `coverage.xml`. Из coverage исключены служебные файлы Alembic и скрипт
`seed_users.py`, создающий демоаккаунты для локальной разработки. Отдельных
тестов этого скрипта нет. Entrypoint остаётся в расчёте общего покрытия.

`just test-no-cov` запускает тот же набор параллельно, полностью отключая
pytest-cov. Измерение покрытия и создание отчётов не выполняются; существующие
`.coverage`, `coverage.xml` и `htmlcov/` не перезаписываются.

Обе команды принимают обычные аргументы pytest: файлы, каталоги, node ID,
несколько путей, фильтры и параметры запуска. Аргументы разбирает сам pytest,
их порядок не меняет выбранный набор тестов. Для ежедневного запуска отдельных
сценариев используйте `test-no-cov`, например:

```bash
just test-no-cov -q tests/unit/application/interactors/test_log_in.py
just test-no-cov tests/unit -k login
just test-no-cov tests/unit tests/integration/application -q
just test-no-cov tests/unit/application/interactors/test_log_in.py::TestLogInInteractor
just test -n 0
```

`just test` измеряет покрытие всего приложения и проверяет порог 90%.
При намеренном запуске только части тестов с coverage можно явно отключить
общий порог: `just test tests/unit --cov-fail-under=0`.

Стиль сохраняет соглашения josko: классы `Test…` для интеракторов, unit-тестов
адаптеров и HTTP; функции для инфраструктурных интеграционных тестов.
Каждый тест следует AAA: подготовка данных, действие, проверка результата.
Проверяются собственные правила и наблюдаемое состояние. Повторные проверки
стандартной библиотеки и одинаковые матрицы ошибок на нескольких уровнях
не нужны; процент покрытия помогает найти пробелы, но не определяет состав тестов.

| Где | Что проверяется |
| --- | --- |
| `unit/application` | Ветвления интеракторов, права доступа, валидаторы |
| `unit/infrastructure` | Логика сессий и контракты криптографических адаптеров без БД |
| `integration/application` | Связка регистрации/входа с настоящими БД и хешированием |
| `integration/infrastructure` | SQL-запросы, ограничения БД, транзакции, согласованность схемы |
| `integration/presentation` | HTTP-контракты, cookie, DI, жизненный цикл сессий |

В `integration/infrastructure/persistence_sqla/test_schema.py` оставлена одна
проверка согласованности схемы: результат настоящих миграций сравнивается с
SQLAlchemy mappings. Она ловит, например, добавленную в mappings колонку без
миграции, даже если ни один сценарий пока не читает эту колонку. Отдельных
проверок устройства Alembic нет; миграции применяются при подготовке каждой БД.

Unit-тест означает проверку небольшого компонента без внешнего I/O; он может
относиться к любому слою. Domain сейчас содержит простые dataclass без отдельных
бизнес-правил: их заполнение проверяется через сценарии приложения. Для них
отдельный каталог тестов не требуется.

Entrypoint — настройки и сборка приложения; отдельных тестов для него нет.
Все пять интеракторов проверяются unit-тестами и HTTP-сценариями с настоящей БД.
Дополнительные интеграционные тесты регистрации и входа проверяют сохранение
пользователя и сессии вместе с настоящим хешированием. Для выхода и проверки прав
отдельные интеграционные файлы не нужны: соответствующая связка уже проверяется
через HTTP в `test_sessions.py`.

Unit-тесты адаптеров проверяют их собственные решения без БД: например, когда
сессия истекает или продлевается и как обрабатывается некорректный хеш.
Интеграционные тесты SQL-адаптеров отдельно проверяют запросы, ограничения и
связи БД, включая случаи, которые не возникают в обычном сценарии интерактора.

### Как добавить или изменить тест

Файл тестов размещается в соответствующем слое. За основу можно взять
ближайший существующий пример:

| Изменение | Пример |
| --- | --- |
| Правило интерактора | [unit-тест регистрации](tests/unit/application/interactors/test_sign_up.py) |
| Валидация входного значения | [проверка пароля](tests/unit/application/validators/test_check_raw_password.py) |
| SQL-запрос или ограничение БД | [тест SQL-адаптера пользователей](tests/integration/infrastructure/adapters/test_user_data_mapper_sqla.py) |
| HTTP-статус, JSON или перевод ошибки | [HTTP-контракт входа](tests/integration/presentation/test_auth_login.py) |
| Сценарий с настоящими интеракторами, БД и cookie | [жизненный цикл сессии](tests/integration/presentation/test_sessions.py) |

Внутри теста сначала подготовьте данные, затем вызовите проверяемое действие,
после него проверьте результат или состояние. Сборка интерактора находится
в фикстуре `interactor` соответствующего класса; при новой зависимости меняется
эта фикстура. Данные для отдельного сценария задаются в самом тесте.

В unit-тестах `mock_*` подменяют интерфейсы. `saved_users` и `saved_sessions`
показывают переданные на сохранение сущности; `cookie_state` — исходящие изменения
cookie. Эти списки не имитируют транзакции: сохранение и откат проверяются
интеграционными тестами с настоящей БД.

В интеграционных тестах `sample_user` создаёт объект без сохранения пользователя.
Для подготовки записи используйте `db_session.add()` и `await db_session.commit()`.
`db_session` и `sessionmaker` работают внутри транзакции текущего теста;
её откат выполняет общая фикстура.

Для HTTP-контракта используйте `client` и `interactor_mocks`, для сценария
с настоящей БД — `full_client`. В классе `TestSessionLifecycle` дополнительно
есть `logged_in_client`, который создаёт пользователя и выполняет вход.
Общие фикстуры добавляются в ближайший `conftest.py`, подготовка для одного
класса остаётся в этом классе.

После изменения сначала запустите нужный файл через `just test-no-cov <путь>`,
затем полный набор `just test` и статические проверки `just check`.

### Устройство тестового окружения

Bootstrap означает подготовку окружения. HTTP — запросы и ответы API.
Отдельных `bootstrap.py` и `http.py` нет: фикстуры размещены в `conftest.py`
рядом с тестами, которые их используют:

- `tests/conftest.py` — общие данные и моки; без БД и автоматических действий.
- `tests/integration/conftest.py` — PostgreSQL, миграции, соединения и транзакции.
- `tests/integration/presentation/conftest.py` — HTTPX-клиенты и Dishka providers.

HTTPX вызывает приложение в памяти, без запуска сетевого сервера. Клиент
`client` подменяет интеракторы для проверки HTTP-контрактов; `full_client`
использует настоящие интеракторы и БД. Оба используют одинаковую настройку
приложения и закрывают DI-контейнер после теста.

Фикстуры ленивые: PostgreSQL запускается только при запросе БД-фикстуры.
Unit-тесты и HTTP-контракты не требуют работающей БД.
Фикстура `postgres_service` запускает `compose.test.yaml` один раз на прогон;
workers синхронизируются через файловую блокировку в общем временном каталоге.
Ожидание запуска Compose ограничено по времени, чтобы сбой Docker не подвешивал
прогон тестов.
Списков имён файлов для определения необходимости БД нет.

Нужен запущенный Docker Desktop. Тестовый PostgreSQL использует отдельный
Compose-проект, порт `55432` на loopback и `tmpfs`, без рабочих `.env` и
постоянных томов. Порт можно переопределить через `TEST_POSTGRES_PORT`.

Каждый worker создаёт свою уникальную временную базу и применяет реальные
миграции. Каждый тест получает внешнюю транзакцию и SAVEPOINT: вызовы `commit()`
в приложении работают, но после теста все его изменения откатываются. При
завершении worker база удаляется, в том числе после ошибок тестов и подготовки.
Жёсткое завершение процесса может оставить базу до перезапуска тестового сервиса.

Для внешнего тестового PostgreSQL задайте `TEST_POSTGRES_HOST`,
`TEST_POSTGRES_PORT`, `TEST_POSTGRES_USER` и `TEST_POSTGRES_PASSWORD`.
Тогда автоматический запуск Docker отключается. Пользователю тестовой БД
нужно право `CREATEDB`. Настройки `POSTGRES_*` рабочего приложения не используются.

Прямой запуск pytest использует те же фикстуры и автоматически подготавливает
БД, когда она нужна:

```bash
uv run --locked --all-groups pytest tests/
```

Остановить тестовый сервис и очистить его временные данные:

```bash
docker compose --env-file /dev/null -f compose.test.yaml down
```
